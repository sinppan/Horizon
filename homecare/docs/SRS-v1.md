## 1. 项目背景与目标

### 1.1 业务背景

面向高端住宅小区的长期空置房提供定期巡检服务：巡检员定期上门通风、放水、检查水电燃气与家电、照料绿植，并以视频和图文报告的形式向不在本地的业主反馈房屋状况。发现问题后提供处理方案，经业主确认后执行并另行收费。

业务模式为按年收费的套餐制（如 2999 元/年含 12 次月检 + 应急响应），核心商业指标是**续费率**，核心客户价值是**安心感**与**可验证的信任**。

### 1.2 系统目标

系统存在的目的不是"管理"，而是三件事：

1. **留证据**：每一次入户从开始到结束都有不可篡改的时间、定位、照片、视频记录，保护业主也保护服务方。
2. **让业主看见**：业主用两分钟就能确认"有人去了、家里没事、钱花得明白"。
3. **让服务可复制**：任何一个经过培训的巡检员，按系统的引导都能完成一次合格的巡检，不漏项、不出错。

### 1.3 成功指标（上线后 6 个月内衡量）

| 指标 | 目标 |
|---|---|
| 巡检记录提交完整率（无漏项、必拍项齐全） | ≥ 98% |
| 巡检完成到报告推送的时长 | ≤ 2 小时（含人工剪辑视频） |
| 业主报告打开率 | ≥ 80% |
| 单次入户平均时长 | ≤ 40 分钟 |
| 系统导致的巡检记录丢失 | 0 |
| 异常工单从发现到业主收到通知 | ≤ 10 分钟 |

### 1.4 系统边界

**系统内**：客户与房屋档案、合同与套餐、巡检任务排班、巡检执行与记录、报告生成与推送、异常工单、通知自动化、年度报告导出、基础看板。

**系统外（第一版不做，详见第 11 章）**：在线支付、电子合同签署、智能路线规划、App 内视频剪辑、业主自助下单、评价系统、多租户/加盟、财务核算、巡检员薪酬、BI 报表。

## 2. 术语定义

| 术语 | 定义 |
|---|---|
| 业主 | 房屋所有人或其授权的家属，是服务的购买方和报告的接收方 |
| 房屋 | 被服务的一套住宅，是系统中大部分数据的挂载对象。一个业主可拥有多套房屋 |
| 巡检员 | 上门执行巡检的服务人员 |
| 管理员 | 服务方的运营人员，负责客户、合同、排班、工单处理 |
| 建档 | 首次入户时对房屋进行的全面记录，形成后续巡检的对照基准 |
| 清单模板 | 一组预定义的检查项，巡检时逐项执行。分多个版本（月检、入冬、入夏、回家前等） |
| 检查项 | 清单中的一条，如"卫生间顶面是否有水渍" |
| 巡检任务 | 对某套房屋在某个计划日期的一次巡检安排 |
| 巡检记录 | 一次巡检任务的执行结果，包含所有检查项结果、照片、视频、读数 |
| 异常 | 巡检中发现的非正常状态，按严重程度分红/黄/绿三级 |
| 异常工单 | 针对一个异常的处理流程记录，从发现到结案 |
| 总体状态 | 一次巡检或一套房屋当前的综合状态，红/黄/绿三色 |
| 读数 | 水表、电表、燃气表的数值，用于跨月比对 |
| 房屋群 | 企业微信中为每套房屋建立的客户群，成员为业主、巡检员、管理员 |

## 3. 用户角色与权限

### 3.1 角色定义

| 角色 | 使用端 | 登录方式 | 典型场景 |
|---|---|---|---|
| 巡检员 | 巡检员端（微信小程序） | 微信授权 + 手机号验证码；账号由管理员预先创建并审批通过后方可登录 | 站在业主家里，单手持机，可能无信号 |
| 业主 | 业主端（微信小程序） | 微信授权 + 手机号验证 [假设]，由管理员预先绑定到房屋 | 人在外地或海外，碎片时间查看 |
| 管理员 | 管理端（Web） | 账号密码 + 企业微信扫码（二选一） | 晚间在电脑前处理当日事务 |
| 超级管理员 | 管理端（Web） | 同管理员 | 系统配置、账号管理、清单模板管理 |

**巡检员的人员类型**（已确认：仅全职与兼职，不使用外部合作人员）：

| 类型 | 定义 | 与系统的关系 |
|---|---|---|
| 全职 | 本公司正式员工 | 可被分配任何任务；可选绑定企业微信身份以接收应用消息 |
| 兼职 | 与公司有兼职协议的个人，非每日出勤 | 同全职，但在排班时按其可用时间段分配（见 FR-STF-04）；入户敏感信息可见时机更严格（见 BR-02a） |

两类人员使用同一个巡检员端，功能一致；差异只体现在准入材料、入户信息可见时机和通知渠道上。

### 3.2 权限矩阵

| 能力 | 巡检员 | 业主 | 管理员 | 超级管理员 |
|---|---|---|---|---|
| 查看分配给自己的当日/本周任务 | ✓ | | ✓ | ✓ |
| 查看任务对应房屋的入户信息（密码、注意事项） | 仅任务当日 | | ✓ | ✓ |
| 查看客户姓名、电话 | ✗ | | ✓ | ✓ |
| 执行巡检、提交记录 | ✓ | | | |
| 创建异常工单 | ✓ | ✓（报修） | ✓ | ✓ |
| 确认/拒绝异常处理方案 | | ✓ | | |
| 查看本人房屋的记录、报告、视频 | | ✓ | ✓ | ✓ |
| 客户、房屋、合同的增删改 | | | ✓ | ✓ |
| 排班、任务分配 | | | ✓ | ✓ |
| 清单模板增删改 | | | | ✓ |
| 账号管理、系统参数配置 | | | | ✓ |
| 导出年度报告 | | ✓（本人房屋） | ✓ | ✓ |

### 3.3 权限业务规则

- **BR-01** 巡检员的数据可见范围按"任务"隔离：只能看到当前分配给自己、且状态为待执行/进行中的任务所关联的房屋信息。任务完成后 24 小时内仍可查看自己提交的记录，之后不可见。
- **BR-02** 房屋的入户敏感信息（门锁密码、钥匙编号、保险箱位置等）对全职巡检员仅在任务计划日期当天 00:00 至 23:59 可见。
- **BR-02a** 对兼职巡检员，入户敏感信息仅在其完成"开始巡检"打卡（定位通过）之后才可见，且任务提交后立即不可见 [假设，见第 13 章问题 3]。
- **BR-03** 巡检员账号停用后，立即失去所有数据访问权限，其历史提交记录保留并标记执行人姓名与人员类型。
- **BR-03a** 巡检员账号必须经管理员审批（见 FR-STF-02）才能首次登录；审批前以手机号登录只能看到"等待审批"页面。
- **BR-04** 一套房屋可绑定多个业主账号（如夫妻、子女），权限相同。[假设] 第一版不区分主副业主。
- **BR-05** 业主只能看到自己名下房屋的数据，看不到巡检员的联系方式、其他客户的任何信息。

## 4. 系统总体架构（需求层面）

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  巡检员端     │  │   业主端      │  │   管理端      │
│ 微信小程序    │  │  微信小程序   │  │   Web 后台    │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └─────────────────┼─────────────────┘
                         │ HTTPS API
                ┌────────▼────────┐
                │    后端服务      │
                │ 业务逻辑 / 规则引擎│
                │ 任务调度 / 通知   │
                └──┬─────┬─────┬──┘
                   │     │     │
          ┌────────▼┐ ┌──▼───┐ ┌▼──────────────┐
          │ 关系数据库│ │对象存储│ │ 外部集成        │
          │ 业务数据  │ │照片视频│ │ 企业微信 / 地图  │
          └─────────┘ └──────┘ └───────────────┘
```

**架构约束（需求层面，不限定具体技术选型）**：

- 三端共用一套后端 API，角色鉴权在后端完成。
- 照片、视频存对象存储，数据库只存引用与元数据。
- 巡检员端必须支持离线执行，网络恢复后自动同步（见 NFR-03）。
- 面向业主的通知走企业微信房屋群，面向巡检员的通知走小程序订阅消息（全职且已绑定企业微信者可同时走应用消息），不自建推送服务。
- 单租户部署，即一套系统只服务一家公司（已确认无加盟/多公司计划，数据模型不做租户隔离）。

| FR-CUS-02 | 客户可关联多套房屋 | P0 |
| FR-CUS-03 | 管理员可为客户生成绑定邀请（二维码或链接），业主在小程序中扫码并验证手机号后完成账号绑定 | P0 |
| FR-CUS-04 | 客户详情页汇总：名下房屋、有效合同、最近一次巡检状态、未关闭工单、到期提醒 | P0 |
| FR-CUS-05 | 客户通知偏好设置：每次巡检都推送 / 仅异常时推送 / 仅月度汇总；推送时段（按业主所在时区的 08:00–22:00 窗口）| P1 |
| FR-CUS-06 | 停用客户时，其名下房屋的所有任务自动取消，但历史记录保留 | P0 |

### 5.2 房屋管理（FR-HSE）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-HSE-01 | 管理员可创建、编辑、停用房屋。基础字段：小区名称、楼栋、单元、房号、详细地址、经纬度（用于定位打卡）、建筑面积、房龄、户型、楼层、是否顶楼、是否一楼 | P0 |
| FR-HSE-02 | 入户信息（敏感字段，受 BR-02 保护）：入户方式（智能锁临时密码 / 实体钥匙 / 物业开门）、钥匙编号、密码获取方式说明、门禁方式、停车说明 | P0 |
| FR-HSE-03 | 相关方联系信息：物业客服电话、物业对接人、楼下邻居联系方式（漏水时用）、业主指定的本地紧急联系人 | P0 |
| FR-HSE-04 | 房屋级服务约定（自由文本 + 结构化开关）：禁止进入的房间、禁止打开的柜子/抽屉、离开时电闸处理方式（全关 / 仅留冰箱 / 不动）、空调是否需要试运行、冰箱过期食品处理方式（直接丢弃 / 拍照询问 / 不处理）、植物处理方式（仅浇水 / 可修剪）| P0 |
| FR-HSE-05 | 房屋可绑定多个业主账号（BR-04） | P0 |
| FR-HSE-06 | 房屋当前状态：根据最近一次巡检记录的总体状态和未关闭工单的最高等级自动计算，取两者较严重者 | P0 |
| FR-HSE-07 | 房屋可设置"暂停服务"状态（业主回来住一段时间），暂停期间不生成任务，合同期不顺延 [假设] | P1 |

### 5.3 房屋建档（FR-ARC）

建档是首次入户时完成的一次性深度记录，是后续所有巡检的对照基准。建档本身作为一种特殊类型的巡检任务执行（使用"建档"清单模板）。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-ARC-01 | 建档模板包含：全屋分空间照片（每个空间至少 4 个方位 + 顶面）、全屋走一遍的连续录像、三表基准读数（拍照 + 手填）、家电清单、植物清单、钥匙与门锁信息核对、业主特殊要求确认 | P0 |
| FR-ARC-02 | 家电清单：每条记录含类别（冰箱/空调/热水器/洗衣机/其他）、品牌、型号、所在位置、照片、当前是否通电运行、备注。至少录入冰箱、热水器、空调 | P0 |
| FR-ARC-03 | 植物清单：每条记录含名称或描述、位置、照片、浇水频率（每次巡检 / 隔次 / 不浇）、浇水量说明、是否可修剪 | P0 |
| FR-ARC-04 | 建档完成后，系统将本次照片标记为"基准照片"，后续巡检中同一检查项的照片可与基准照片并排对比 | P1 |
| FR-ARC-05 | 建档记录在业主端的"房屋档案"中可见，让业主确认系统对其房屋的了解是否准确；业主可在 7 天内提出修改意见（通过工单） | P1 |
| FR-ARC-06 | 建档可重新执行（如装修后），新建档覆盖基准照片和读数，旧建档归档可查 | P2 |

| FR-CTR-06 | 合同终止：需填写终止原因，终止后未执行的任务自动取消 | P0 |
| FR-CTR-07 | 应急出勤次数计数：每次应急类工单结案时扣减合同的剩余应急次数，用完后新应急工单提示管理员需另行收费 | P1 |
| FR-CTR-08 | 一套房屋同一时间只能有一份生效合同 | P0 |

| 编号 | 需求 | 优先级 |
|---|---|---|

| FR-STF-03 | （v1.2 移除：原为外部合作人员服务范围配置） | — |
| FR-STF-04 | 兼职人员可用时间：按星期几 + 上午/下午/全天维护可用时段，排班视图中对不可用时段分配任务时给出警告（不阻止） | P1 |
| FR-STF-05 | 人员状态：待审批 / 在职 / 暂停 / 停用。暂停期间不可被分配新任务，已分配任务保留并提示管理员改派；停用触发 BR-03 | P0 |
| FR-STF-06 | 材料有效期提醒：无犯罪记录证明、协议到期前 30 天提醒管理员更新 | P1 |

### 7.6 巡检员端业务规则

- **BR-06** 一个巡检员同一时间只能有一个"进行中"的任务。

### 10.2 通知与自动化规则（FR-NTF）

已确认方案：面向业主的通知以**企业微信客户群（房屋群）**为主，**小程序订阅消息**为辅。短信仅用于红色异常且企业微信消息发送失败时的兜底。

**房屋群的组成与消息发送方式**：

- 每套房屋一个企业微信客户群，成员为：业主（及其绑定的家属账号）+ 管理员。**巡检员不入群**。原因：巡检员包含兼职人员，流动性相对高，不应与业主建立直接联系（也符合 BR-05）；巡检员更换时业主侧无感知。
- 所有"巡检开始 / 巡检完成 / 报告 / 工单"类消息由系统通过企业微信自建应用（或群机器人）以统一身份发送，消息中带巡检员姓名。
- 管理员在群内以个人企业微信身份与业主沟通，系统消息与人工沟通在同一个群内，业主只需要一个入口。
- 面向巡检员的通知走小程序订阅消息（全职且已绑定企业微信者同时走应用消息，FR-STF-08）。订阅消息需巡检员在小程序内授权，首次登录时引导一次性授权（勾选"总是保持以上选择"）。

| 编号 | 触发 | 接收方 | 渠道 | 优先级 |

**通知业务规则**：

## 13. 待确认问题（需业务方逐条回答）

以下问题当前以 [假设] 方案写入文档，答案不同会导致需求变更。按影响程度排序。

### 已确认（v1.1）

| 问题 | 结论 | 文档落点 |
|---|---|---|
| 巡检员身份 | 全职 + 兼职（v1.2 更正：不使用外部合作人员） | 3.1 人员类型、BR-02a/03a、5.5 FR-STF、FR-SCH-03 |
| 业主通知主渠道 | 企业微信房屋群为主，消息发群里 | 10.2，巡检员不入群、系统身份发送 |
| 视频成片 | 7 段引导拍摄 + 人工剪辑后上传 | 7.4 |
| 加盟 / 多公司 | 无此计划 | 第 4 章单租户、第 11 章 |

### 影响架构或核心流程（请优先回答）

1. **第一年预期规模**：房屋数量、巡检员人数（全职/兼职大致比例）、覆盖的城市数量。当前假设 ≤ 300 套、≤ 10 人、单城市。这影响部署方案和成本。

### 影响具体功能设计

2. **读数阈值**：BR-10 的水表 0.5/2 m³、电表 150%/300%、燃气 > 0 是否合理？是否有经验数据？
3. **兼职人员的入户信息可见时机**：BR-02a 当前设为"打卡通过后可见、提交后不可见"。是否需要更严格，例如必须由管理员在群内实时发送密码、系统不展示？或者要求兼职人员首次服务某房屋时必须由全职人员陪同？也可以放宽为与全职一致（任务当天可见）。
4. **兼职人员的任务范围**：兼职是否可以做建档和应急任务，还是只做常规月检？当前假设不限制任务类型。
5. **定位打卡距离**：200 米是否合适？高层住宅定位漂移常见，太严会误报，太松失去意义。
6. **一套房屋多个业主**：是否需要区分"主业主"（能确认付费工单）和"查看者"（只能看）？当前假设权限相同。
7. **业主确认工单的时效与超时处理**：待确认超 24 小时提醒管理员人工跟进，完工待验收 72 小时自动结案。这两个时长是否合适？
8. **应急响应的 SLA**：套餐承诺的应急响应时效是多少（2 小时 / 4 小时 / 当天）？是否按红黄分级？系统需据此设置超时提醒。
9. **暂停服务**：业主回来住一段时间要求暂停巡检，暂停期间合同期是否顺延？当前假设不顺延。
10. **套餐种类**：第一版有几种套餐？各自的频次、价格、应急次数是什么？是否有按季付的选项？
11. **巡检时间窗**：是否允许业主指定具体时间段（如"只能工作日上午"）？当前只支持业主请求调整日期区间，由管理员确认。
12. **家电巡检深度**：对空调、热水器是"目视 + 试运行"还是只目视？试运行需要通电、增加时长和风险，影响清单模板和服务约定。
13. **冰箱与电闸的默认处理**：空置房离开时电闸处理（全关 / 仅留冰箱 / 不动）由业主逐户约定，还是公司有统一默认？

### 影响合规与资料

14. **数据保留期**：照片保留合同期 + 1 年、视频原片 90 天是否合适？是否有保险公司或法律顾问对取证资料保留期有要求？
15. **隐私政策、服务协议、巡检人员行为规范与保密协议**：是否已有法律顾问起草的版本？系统需在业主/巡检员首次进入时展示并记录同意（FR-STF-09）。
16. **保险**：是否已购买公众责任险/雇主责任险？兼职人员是否在雇主责任险覆盖范围内（兼职通常需要单独约定）？若保险公司对巡检记录格式有要求，需纳入报告模板。
17. **巡检人员准入材料**：FR-STF-01 列出的身份证、无犯罪记录证明、健康证是否齐全？兼职是否要求与全职相同的材料？
18. **公司品牌信息**：报告、年度报告、分享页需要的公司名称、Logo、客服电话、服务承诺文案。

### 其他

19. **巡检员薪酬是否按单计算**：兼职大概率按单结算。第一版不做薪酬模块，但需确保任务数据可按人员、按月导出供手工核算，是否需要特定的导出格式？
20. **物业对接**：物业通知异常时，是否希望给物业一个最简单的报修入口（如一个二维码表单），还是全部通过电话到管理员？
21. **海外业主比例**：如果海外业主占比高，需要确认 CDN 境外可达性、企业微信在境外的可用性、以及是否真的不需要英文界面。

## 14. 建议的实施阶段

不按日历时间划分，按可交付的能力划分。每个阶段结束都应能在真实房屋上跑通对应流程。

| 阶段 | 交付能力 | 验证方式 |
|---|---|---|
| 阶段 0：数据与模板 | 数据模型落地；客户、房屋、合同、套餐管理；巡检人员档案与审批（FR-STF）；清单模板管理并录入附录 A 的标准月检模板 | 管理员能录入 5 套真实房屋和合同，并为 1 名全职、1 名兼职完成准入 |
| 阶段 1：巡检闭环 | 巡检员端完整执行流程（打卡 → 清单 → 拍照 → 读数 → 异常 → 离开检查 → 提交）；离线能力；自动生成任务 | 巡检员在真实房屋完成 3 次巡检，无网络环境下完成 1 次 |
| 阶段 2：业主可见 | 报告生成；成片上传；企业微信通知；业主端首页、报告页、历史页、档案页 | 3 位真实业主收到并打开报告 |
| 阶段 3：异常闭环 | 工单全流程；业主确认；红色异常即时通知；读数预警；管理端工单看板 | 制造 1 个真实异常走完全流程 |
| 阶段 4：运营支撑 | 今日看板；到期提醒；年度报告生成与 PDF 导出；记录审核；系统参数配置；操作日志 | 管理员仅凭系统完成一天的运营 |
| 阶段 5：P1 收尾 | 基准照片对比、房屋级清单覆盖、季节性专项自动生成、日期调整请求、通知偏好、月度汇总 | 全量客户切换到系统 |

