## 1. 项目背景与目标

### 1.1 业务背景

面向高端住宅小区的长期空置房提供定期巡检服务：巡检员定期上门通风、放水、检查水电燃气与家电、照料绿植，并以视频和图文报告的形式向不在本地的业主反馈房屋状况。发现问题后提供处理方案，经业主确认后执行并另行收费。

业务模式为按年收费的套餐制（如 2999 元/年含 12 次月检 + 应急响应），核心商业指标是**续费率**，核心客户价值是**安心感**与**可验证的信任**。

### 1.2 系统目标

系统存在的目的不是"管理"，而是三件事：

1. **留证据**：每一次入户从开始到结束都有不可篡改的时间、定位、照片、视频记录，保护业主也保护服务方。
2. **让业主看见**：业主用两分钟就能确认"有人去了、家里没事、钱花得明白"。
3. **让服务可复制**：任何一个经过培训的巡检员，按系统的引导都能完成一次合格的巡检，不漏项、不出错。

### 1.3 成功指标（上线后 6 个月内衡量）

| 指标 | 目标 |
|---|---|
| 巡检记录提交完整率（无漏项、必拍项齐全） | ≥ 98% |
| 巡检完成到报告推送的时长 | ≤ 2 小时（含人工剪辑视频） |
| 业主报告打开率 | ≥ 80% |
| 单次入户平均时长 | ≤ 40 分钟 |
| 系统导致的巡检记录丢失 | 0 |
| 异常工单从发现到业主收到通知 | ≤ 10 分钟 |

### 1.4 系统边界

**系统内**：客户与房屋档案、合同与套餐、巡检任务排班、巡检执行与记录、报告生成与推送、异常工单、通知自动化、年度报告导出、基础看板。

**后续版本（已确认纳入规划，详见第 15 章）**：保养手册、季节专项目录、车辆照看、文书代收、预约开门陪同、离家封存、回家准备编排、行程日历联动、出租查验、装修监理、交易支持、独居父母探访。

**系统外（第一版不做，详见第 11 章）**：在线支付、电子合同签署、智能路线规划、App 内视频剪辑、业主自助下单、评价系统、多租户/加盟、财务核算、巡检员薪酬、BI 报表。

## 2. 术语定义

| 术语 | 定义 |
|---|---|
| 业主 | 房屋所有人或其授权的家属，是服务的购买方和报告的接收方 |
| 房屋 | 被服务的一套住宅，是系统中大部分数据的挂载对象。一个业主可拥有多套房屋 |
| 巡检员 | 上门执行巡检的服务人员 |
| 管理员 | 服务方的运营人员，负责客户、合同、排班、工单处理 |
| 建档 | 首次入户时对房屋进行的全面记录，形成后续巡检的对照基准 |
| 清单模板 | 一组预定义的检查项，巡检时逐项执行。分多个版本（月检、入冬、入夏、回家前等） |
| 检查项 | 清单中的一条，如"卫生间顶面是否有水渍" |
| 巡检任务 | 对某套房屋在某个计划日期的一次巡检安排 |
| 巡检记录 | 一次巡检任务的执行结果，包含所有检查项结果、照片、视频、读数 |
| 异常 | 巡检中发现的非正常状态，按严重程度分红/黄/绿三级 |
| 异常工单 | 针对一个异常的处理流程记录，从发现到结案 |
| 总体状态 | 一次巡检或一套房屋当前的综合状态，红/黄/绿三色 |
| 读数 | 水表、电表、燃气表的数值，用于跨月比对 |
| 房屋群 | 企业微信中为每套房屋建立的客户群，成员为业主、巡检员、管理员 |

## 3. 用户角色与权限

### 3.1 角色定义

| 角色 | 使用端 | 登录方式 | 典型场景 |
|---|---|---|---|
| 巡检员 | 巡检员端（微信小程序） | 微信授权 + 手机号验证码；账号由管理员预先创建并审批通过后方可登录 | 站在业主家里，单手持机，可能无信号 |
| 业主 | 业主端（微信小程序） | 微信授权 + 手机号验证 [假设]，由管理员预先绑定到房屋 | 人在外地或海外，碎片时间查看 |
| 运营管理员 | 管理端（Web） | 账号密码 + 第二因素（企业微信扫码或短信验证码），强制双因素（PRV-19） | 晚间在电脑前处理客户、排班、工单 |
| 超级管理员 | 管理端（Web） | 同运营管理员 | 系统配置、账号管理、清单模板管理、敏感数据与审计 |

> 文中单独出现的"管理员"指运营管理员与超级管理员均可执行的能力。

**巡检员的人员类型**（已确认：仅全职与兼职，不使用外部合作人员）：

| 类型 | 定义 | 与系统的关系 |
|---|---|---|
| 全职 | 本公司正式员工 | 可被分配任何任务；可选绑定企业微信身份以接收应用消息 |
| 兼职 | 与公司有兼职协议的个人，非每日出勤 | 同全职，但在排班时按其可用时间段分配（见 FR-STF-04）；入户敏感信息可见时机更严格（见 BR-02a） |

两类人员使用同一个巡检员端，功能一致；差异只体现在准入材料、入户信息可见时机和通知渠道上。

### 3.3 权限业务规则

- **BR-01** 巡检员的数据可见范围按"任务"隔离：只能看到当前分配给自己、且状态为待执行/进行中的任务所关联的房屋信息。任务完成后 24 小时内仍可查看自己提交的记录，之后不可见。
- **BR-02** 房屋的入户敏感信息（门锁密码、钥匙编号、保险箱位置等）对全职巡检员仅在任务计划日期当天 00:00 至 23:59 可见。
- **BR-02a** 对兼职巡检员，入户敏感信息仅在其完成"开始巡检"打卡（定位通过）之后才可见，且任务提交后立即不可见 [假设，见第 13 章问题 4]。
- **BR-03** 巡检员账号停用后，立即失去所有数据访问权限，其历史提交记录保留并标记执行人姓名与人员类型。
- **BR-03a** 巡检员账号必须经管理员审批（见 FR-STF-02）才能首次登录；审批前以手机号登录只能看到"等待审批"页面。
- **BR-04** 一套房屋可绑定多个业主账号（如夫妻、子女），权限相同。[假设] 第一版不区分主副业主。
- **BR-05** 业主只能看到自己名下房屋的数据，看不到巡检员的联系方式、其他客户的任何信息。
- **BR-05a** 巡检员端在任何页面都不显示业主姓名、手机号、微信（统一显示"业主"）；巡检员与业主之间的沟通一律经由管理员（PRV-13）。
- **BR-05b** 巡检员端任务列表只显示小区与楼栋，详细房号仅在任务详情页展示；经纬度仅用于打卡比对不展示（PRV-14）。
- **BR-05c** 任务完成 24 小时后，巡检员端对该任务的全部数据（含照片）不可见，本地缓存自动清除（PRV-16/21）。
- **BR-05d** 任何对业主联系方式、入户信息、照片原片、巡检员证件的读取都写入敏感数据访问日志（PRV-24），业主可在隐私中心查看与其房屋相关的记录（PRV-28）。

## 4. 系统总体架构（需求层面）

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  巡检员端     │  │   业主端      │  │   管理端      │
│ 微信小程序    │  │  微信小程序   │  │   Web 后台    │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └─────────────────┼─────────────────┘
                         │ HTTPS API
                ┌────────▼────────┐
                │    后端服务      │
                │ 业务逻辑 / 规则引擎│
                │ 任务调度 / 通知   │
                └──┬─────┬─────┬──┘
                   │     │     │
          ┌────────▼┐ ┌──▼───┐ ┌▼──────────────┐
          │ 关系数据库│ │对象存储│ │ 外部集成        │
          │ 业务数据  │ │照片视频│ │ 企业微信 / 地图  │
          └─────────┘ └──────┘ └───────────────┘
```

**架构约束（需求层面，不限定具体技术选型）**：

- 三端共用一套后端 API，角色鉴权与城市数据范围过滤（FR-CTY-03）在后端完成。
- 5 个城市共用同一套部署与数据库，城市只是业务维度，不做分库。
- 照片、视频存对象存储，数据库只存引用与元数据。
- 巡检员端必须支持离线执行，网络恢复后自动同步（见 NFR-03）。
- 面向业主的通知走企业微信房屋群，面向巡检员的通知走小程序订阅消息（全职且已绑定企业微信者可同时走应用消息），不自建推送服务。
- 单租户部署，即一套系统只服务一家公司（已确认无加盟/多公司计划，数据模型不做租户隔离）。

## 5. 功能需求 · 基础数据模块

### 5.0 城市与小区（FR-CTY）

业务方已确认第一年覆盖 **5 个城市、约 500 套房屋**。系统仍为单租户、单套部署，但"城市"与"小区"需作为一级实体，用于数据范围划分、排班聚合、季节与天气触发、物业联动。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-CTY-01 | 城市：超级管理员维护城市列表（名称、所属气候区用于季节推荐、启用状态）；每个小区、每名巡检员、每名运营管理员都归属于一个或多个城市 | P0 |
| FR-CTY-02 | 小区（Community）实体：名称、所属城市、地址与经纬度中心点、物业公司名称、物业 24 小时值班电话、物业对接人（姓名、电话，L3）、合作状态（已签约 / 洽谈中 / 无合作）、合作协议附件、备注。房屋通过 `community_id` 关联小区，不再以文本存小区名 | P0 |
| FR-CTY-03 | 运营管理员的数据范围：超级管理员为每名运营管理员分配可见城市（一个或多个）；其客户、房屋、任务、工单、看板均按所分配城市过滤；超级管理员全局可见 | P0 |
| FR-CTY-04 | 巡检员的服务城市：人员档案标注可服务城市（通常 1 个）；排班时只能分配到其服务城市内的任务 | P0 |
| FR-CTY-05 | 小区级汇总：小区详情页显示该小区生效房屋数、本月任务、未关闭工单、物业联动信息；FR-SCH-02 的同小区聚合、FR-SEA-03 的天气批量触发、FR-ELD-13/14 的联动与白名单都以小区实体为对象 | P0 |
| FR-CTY-06 | 管理端全局城市切换器：看板、房屋总览、排班日历、工单看板均可按城市筛选；运营管理员默认显示其第一个分配城市 | P0 |
| FR-CTY-07 | 城市级运营指标（P2 的 FR-ADM-08 增加城市维度）：各城市房屋数、完成率、异常率、续约率对比 | P2 |

### 5.1 客户管理（FR-CUS）

| 编号 | 需求 | 优先级 |
|---|---|---|

### 7.6 巡检员端业务规则

- **BR-06** 一个巡检员同一时间只能有一个"进行中"的任务。
- **BR-07** 巡检记录推送给业主的前置条件：记录已提交 + 成片已上传（或管理员明确选择"无视频推送"并填写原因）。
- **BR-08** 巡检开始时间与结束时间之差小于 15 分钟的记录，系统标记为"时长异常"，管理员审核后才能推送。
- **BR-09** 红色异常在巡检员提交该检查项的瞬间即触发通知（不等整个巡检完成），见 FR-NTF-07。
- **BR-10** 读数阈值 [假设，待确认]：水表当月用量 > 0.5 m³ 标黄、> 2 m³ 标红；电表当月用量超过房屋历史平均值的 150% 标黄、300% 标红（无历史时首月不判断）；燃气表当月用量 > 0 标黄（空置房燃气不应有消耗）。阈值在系统参数中可配置。

### 10.2 通知与自动化规则（FR-NTF）

已确认方案：面向业主的通知以**企业微信客户群（房屋群）**为主，**小程序订阅消息**为辅。短信仅用于红色异常且企业微信消息发送失败时的兜底。

**房屋群的组成与消息发送方式**：

- 每套房屋一个企业微信客户群，成员为：业主（及其绑定的家属账号）+ 管理员。**巡检员不入群**。原因：巡检员包含兼职人员，流动性相对高，不应与业主建立直接联系（也符合 BR-05）；巡检员更换时业主侧无感知。
- 所有"巡检开始 / 巡检完成 / 报告 / 工单"类消息由系统通过企业微信自建应用（或群机器人）以统一身份发送，消息中带巡检员姓名。
- 管理员在群内以个人企业微信身份与业主沟通，系统消息与人工沟通在同一个群内，业主只需要一个入口。
- 面向巡检员的通知走小程序订阅消息（全职且已绑定企业微信者同时走应用消息，FR-STF-08）。订阅消息需巡检员在小程序内授权，首次登录时引导一次性授权（勾选"总是保持以上选择"）。

| 编号 | 触发 | 接收方 | 渠道 | 优先级 |
|---|---|---|---|---|
| FR-NTF-01 | 巡检开始 | 房屋群 | 企业微信群消息（系统身份） | P0 |
| FR-NTF-02 | 巡检完成 | 房屋群 | 企业微信群消息（系统身份） | P0 |
| FR-NTF-03 | 报告可查看（成片已上传） | 业主 | 群消息 + 小程序订阅消息（含报告卡片链接） | P0 |
| FR-NTF-04 | 工单待业主确认 | 业主 | 群消息 + 订阅消息 | P0 |

### 影响架构或核心流程（请优先回答）

1. ~~第一年预期规模~~ 已确认（v1.7）：约 500 套房屋、5 个城市、巡检员全职:兼职 = 8:2。落点：5.0 FR-CTY（城市与小区实体）、NFR-13/13a。衍生问题见 32、33。
2. **巡检员完全不知道业主是谁**：v1.3 起巡检员端不显示业主姓名与联系方式（BR-05a）。这意味着现场被物业、邻居问起时巡检员只能以房屋编号和公司名义应答，所有与业主的沟通经管理员中转。是否接受这种运营方式？

### 影响具体功能设计

3. **读数阈值**：BR-10 的水表 0.5/2 m³、电表 150%/300%、燃气 > 0 是否合理？是否有经验数据？
4. **兼职人员的入户信息可见时机**：BR-02a 当前设为"打卡通过后可见、提交后不可见"。是否需要更严格，例如必须由管理员在群内实时发送密码、系统不展示？或者要求兼职人员首次服务某房屋时必须由全职人员陪同？也可以放宽为与全职一致（任务当天可见）。
5. **视频剪辑由谁执行**：v1.3 设为管理员专人剪辑（FR-INS-D 说明、PRV-39），原片不留在巡检员设备上。如果前期人手少、希望巡检员自己剪，需重新设计剪辑环节的设备与删除约束。
6. **兼职人员的任务范围**：兼职是否可以做建档和应急任务，还是只做常规月检？当前假设不限制任务类型。
7. **定位打卡距离**：200 米是否合适？高层住宅定位漂移常见，太严会误报，太松失去意义。
8. **一套房屋多个业主**：是否需要区分"主业主"（能确认付费工单）和"查看者"（只能看）？当前假设权限相同。
9. **业主确认工单的时效与超时处理**：待确认超 24 小时提醒管理员人工跟进，完工待验收 72 小时自动结案。这两个时长是否合适？
10. **应急响应的 SLA**：套餐承诺的应急响应时效是多少（2 小时 / 4 小时 / 当天）？是否按红黄分级？系统需据此设置超时提醒。
11. ~~暂停服务是否顺延~~ 已确认（v1.5）：不顺延、不退费、折算为回家准备或陪同开门额度，见 FR-HSE-07。
12. **套餐种类**：第一版有几种套餐？各自的频次、价格、应急次数是什么？是否有按季付的选项？
13. **巡检时间窗**：是否允许业主指定具体时间段（如"只能工作日上午"）？当前只支持业主请求调整日期区间，由管理员确认。
14. **家电巡检深度**：对空调、热水器是"目视 + 试运行"还是只目视？试运行需要通电、增加时长和风险，影响清单模板和服务约定。
15. **冰箱与电闸的默认处理**：空置房离开时电闸处理（全关 / 仅留冰箱 / 不动）由业主逐户约定，还是公司有统一默认？

16. **数据保留期**：照片保留合同期 + 1 年、视频原片 90 天转低频 / 180 天删除是否合适？是否有保险公司或法律顾问对取证资料保留期有要求？
17. **隐私政策、服务协议、巡检人员行为规范与保密协议**：是否已有法律顾问起草的版本？系统需在业主/巡检员首次进入时展示并记录同意（FR-OWN-13、FR-STF-09）。

## 14. 建议的实施阶段

不按日历时间划分，按可交付的能力划分。每个阶段结束都应能在真实房屋上跑通对应流程。

|---|---|---|
| 阶段 0：数据与模板 | 数据模型落地（含数据分级标注、L4 字段级加密、私有桶与签名 URL）；城市与小区实体及运营管理员数据范围（FR-CTY）；客户、房屋（含禁拍区域）、合同、套餐管理；巡检人员档案与审批（FR-STF）；管理端双因素与两级管理员；清单模板管理并录入附录 A 的标准月检模板 | 管理员能录入 5 套真实房屋和合同，并为 1 名全职、1 名兼职完成准入 |
